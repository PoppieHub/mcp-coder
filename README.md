# mcp-coder

`mcp-coder` — локальный MCP-сервер со stdio-транспортом. Он делегирует ограниченные, чётко сформулированные задачи модели, совместимой с Anthropic Messages API. Claude Code или Codex остаётся основной моделью: он планирует работу и проверяет результат; бинарник выступает только самостоятельным исполнителем.

## Сборка

```bash
go build -trimpath -o mcp-coder ./cmd/mcp-coder
MCP_LLM_TOKEN='…' MCP_LLM_BASE_URL='https://llm.corp.ru/api' MCP_LLM_MODEL=coder-medium ./mcp-coder doctor
```

Процессу необходимы `MCP_LLM_TOKEN`, `MCP_LLM_BASE_URL` и `MCP_LLM_MODEL`. Запросы направляются на `${MCP_LLM_BASE_URL}/v1/messages`; название модели не зашито в код. Для переключения модели пересборка не нужна:

```bash
MCP_LLM_MODEL=coder ./mcp-coder
MCP_LLM_MODEL=coder-mini ./mcp-coder
```

Доступные ограничения: `MCP_MAX_AGENT_STEPS` (24), `MCP_MAX_INPUT_CHARS` (12000), `MCP_MAX_FILE_CHARS` (24000), `MCP_MAX_TOTAL_CONTEXT_CHARS` (160000), `MCP_MAX_OUTPUT_TOKENS` (3000), `MCP_REQUEST_TIMEOUT_MS` (60000) `MCP_COMMAND_TIMEOUT_MS` (60000) и `MCP_TASK_TIMEOUT_MS` (600000, 10 минут; диапазон 1000–3600000).

`MCP_MAX_FILE_CHARS` ограничивает один ответ `read_file`, а не размер читаемого файла: файл крупнее лимита возвращается окном строк с пометкой, с какого `offset` продолжить, и читается за несколько вызовов. Окно задаётся аргументами `offset` (1-based номер первой строки) и `limit` (число строк).

Задача останавливается по первому достигнутому лимиту: шагов или общего времени. Таймаут задачи распространяется на подготовку контекста, запросы модели и команды; выполненные изменения не откатываются. `update_settings` принимает `taskTimeoutMs` и `maxAgentSteps` только для следующих задач до перезапуска сервера. Для постоянных значений используйте переменные окружения или настройки расширения.

## Claude Code

Не меняйте `ANTHROPIC_BASE_URL` и `ANTHROPIC_MODEL` у Claude Code. Добавьте сервер как отдельный MCP-инструмент; переменные `MCP_*` будут доступны только дочернему процессу:

```bash
claude mcp add mcp-coder --env MCP_LLM_TOKEN --env MCP_LLM_BASE_URL --env MCP_LLM_MODEL -- /absolute/path/mcp-coder
```

## Claude Desktop

Для установки через UI Claude Desktop соберите локальное macOS-расширение DXT:

```bash
chmod +x scripts/package-claude-dxt.sh
scripts/package-claude-dxt.sh
```

Появится `dist/mcp-coder.dxt`. В Claude Desktop откройте **Settings → Extensions → Advanced settings → Install Extension…**, выберите этот файл и введите токен в показанной форме. Токен отмечен как sensitive и не включается в архив. Расширение собирается под текущую архитектуру macOS; для другого Mac создайте архив на нём заново.

## Codex

Добавьте stdio MCP server в конфигурацию Codex (точный интерфейс настройки зависит от клиента):

```toml
[mcp_servers.mcp-coder]
command = "/absolute/path/mcp-coder"

[mcp_servers.mcp-coder.env]
MCP_LLM_TOKEN = "..."
MCP_LLM_BASE_URL = "https://llm.corp.ru/api"
MCP_LLM_MODEL = "coder-medium"
```

`execute_coding_task` предназначен для реализации задачи, а `ask_coder` — для коротких запросов только на чтение: пути из `files` читаются внутри workspace тем же безопасным путём, что и в задаче, и прикладываются к вопросу (до 10 файлов, файл крупнее `MCP_MAX_FILE_CHARS` приходит усечённым окном, недоступные перечисляются в `warnings`). По умолчанию coding-задача не может завершиться успешно без наблюдаемого изменения файла, успешной проверки и tool-вызова `finalize`. Для исследовательской задачи укажите `readOnly: true`; при необходимости контракт можно явно уточнить полями `requireChanges`, `requireVerification` и `allowedChangePaths`.

Для экономии токенов основной модели делегируйте связанный объём написания кода, документации или тестов одним вызовом: укажите точные файлы, требуемые изменения, критерии результата и уже известный контекст. Исполнитель группирует независимые инструменты в одном ответе и выполняет только нужные проверки. Для документации или точных замен, которые проверит основная модель, можно явно передать `requireVerification: false`; для кода и тестов оставьте проверку включённой и задайте узкую команду. Скорость API этим не меняется: цель — сократить число обращений и повторную разведку.

Успешный результат содержит `diff` изменённых файлов (`git diff`, до 6000 символов), поэтому оркестратору не нужно читать изменения отдельным шагом.

У исполнителя есть безопасные `create_file` и `edit_file`, а также `run_go_test` для одного относительного Go-пакета (`./internal/tools`) или всего модуля (`./...`). Произвольный shell по-прежнему недоступен.

Проверки (`run_verification`) не привязаны к конкретному стеку: разрешено то, что репозиторий объявил сам — скрипт из его `package.json` (`npm`/`pnpm`/`yarn`/`bun run <script>`, а также короткая форма `npm test`), цель из `Makefile`, `justfile` или `Taskfile.yml`, либо штатная команда тулчейна (`go test|vet|build`, `cargo test|clippy|check|build`, `pytest`, `tox`). Дополнительные аргументы — только пути внутри workspace: флаг увёл бы проверку на чужой конфиг, поэтому нужные флаги проект прописывает в своей команде. Имя скрипта без раннера (`verify`, `run verify`) отклоняется с полной формой команды в тексте ошибки: раннер выбирается по полю `packageManager` и локфайлу проекта.

Одна и та же проверка не выполняется дважды на неизменившихся файлах: повтор отдаётся из кеша задачи с пометкой в ответе инструмента и не дублирует запись в `verification`. Любая успешная правка файла сбрасывает кеш, поэтому после изменения проверка запускается заново. Отклонённая allowlist'ом команда проверкой не считается: она не запускалась, не попадает в `verification` и не кешируется, поэтому правильную форму можно вызвать сразу же.

`execute_coding_task` дополнительно принимает необязательный `projectContext`: краткий hint основной модели, например запрет на legacy-подход. Передавайте уже найденные факты, чтобы исполнитель не повторял исследование; он уточняет только недостающее для задачи. Перед изменением executor обнаруживает только известные instruction-файлы (`AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md` и релевантные README), учитывает вложенные правила по пути suggested files и передаёт модели небольшой список соседних файлов для поиска уже существующих patterns. Явные constraints задачи имеют приоритет над `projectContext`, затем применяются instructions и локальный код.

Если активные conventions конфликтуют и безопасно выбрать подход нельзя, результат имеет статус `needs_clarification`; основной модели нужно принять решение. В успешном результате поле `conventionsUsed` содержит только пути применённых правил и соседних patterns, без их содержимого.

Внутри бинарника MCP adapter вызывает независимый executor core. Core можно использовать из будущего UI без изменения agent loop. Он выдаёт lightweight in-process events (`task.started`, discovery, agent/tool, file, verification и final status); сейчас они не требуют consumer, не создают background process и не записываются на диск.

## Безопасность и ограничения

Все файловые операции проходят через единый resolver workspace: абсолютные пути, traversal, выход через symbolic link и распространённые secret-файлы запрещены. У агента нет shell-инструмента. Проверки запускаются массивом аргументов и с timeout, и только те, что объявил сам репозиторий (скрипты `package.json`, цели `Makefile`/`justfile`/`Taskfile.yml`) или штатный тулчейн; аргументы допускаются только как пути внутри workspace. Git используется только для `status` и `diff`: сервер не делает commit, reset, restore или clean. Размеры файлов, вывода, контекста, число шагов и повторы API ограничены. Логи пишутся только в stderr и не содержат учётных данных.

`doctor` проверяет локальную конфигурацию без сети. `doctor --api` выполняет opt-in безопасную проверку Messages API и tool-use roundtrip с synthetic tool; файловые, Git и verification-инструменты при этом не используются. Токен не выводится.
